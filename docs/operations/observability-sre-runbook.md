# 관측성·오류·보안 운영 런북

## 1. 목적과 적용 범위

이 문서는 주문, 결제 확인, 리포트 생성, 리포트 보관, 인증, 관리자 API 장애를 개인정보나 비밀정보 없이 추적하기 위한 벤더 중립 운영 기준이다. 대상은 Cloud Run API와 이를 호출하는 프론트엔드다.

초기 경보 임계값은 출시 전 가드레일이다. 운영 트래픽 2주 또는 요청 1,000건 이상을 확보한 뒤 정상 구간의 p50, p95, 오류율을 기준으로 조정한다. 임계값을 조정해도 아래 개인정보 금지, 서버 권한 검증, 실패 폐쇄 원칙은 완화하지 않는다.

현재 판매 중이며 변경 금지 계약으로 취급하는 상품 ID는 다음 다섯 개다.

- general-signature
- past-life-goblin
- love-reading
- love-reunion
- match-couple

historical entitlement와 archive 운영 로그에는 SERVER_PRODUCT_CATALOG에 등록된 archived ID가 나타날 수 있다. 대시보드와 로그 필터는 SERVER_PRODUCT_CATALOG 전체를 기준으로 하며 archived ID를 누락하거나 임의로 변경하지 않는다.

## 2. 로그 안전 원칙

구조화 로그는 명시적 허용 목록만 기록한다.

| 필드 | 의미 | 운영 주의 |
| --- | --- | --- |
| timestamp | 서버 기록 시각 | UTC ISO-8601 |
| severity | DEBUG, INFO, WARNING, ERROR | 응답 상태와 운영 이벤트에 맞춤 |
| event | http_request 또는 허용된 운영 이벤트 | 자유 서술 금지 |
| requestId | X-Request-ID로 전달된 요청 식별자 | 고객 문의에는 이 값만 요청 |
| route | 정규화된 서버 라우트 | 원본 URL 쿼리 문자열 금지 |
| status | HTTP 상태 | 숫자만 기록 |
| latency | 서버 처리 시간(ms) | 클라이언트 체감 시간과 구분 |
| errorCode | 표준 대문자 오류 코드 | 예외 메시지 원문 금지 |
| productId | 서버 카탈로그로 검증된 상품 ID | 표시 이름이나 자유 입력 금지 |
| orderHash | sha256: 접두사의 단축 해시 | 원본 주문 ID가 아니며 권한 근거로 사용 금지 |
| provider | 허용 목록의 외부 제공자 식별자 | 엔드포인트나 계정 정보 금지 |
| degraded | 정상 품질보다 저하되었는지 여부 | 폴백 증가 경보의 분모·분자에 사용 |

provider는 외부 호출 실행 또는 실패 phase의 확정 증거가 아니다. 인증이 성공한 뒤 router가 해당 단계의 주 책임 provider를 설정하므로 오류 요청에서는 route primary responsibility만 뜻할 수 있다. report 성공 응답의 trusted 결과로 기록된 provider만 결과 생성 provider를 뜻한다. 여러 의존성을 거치는 복합 단계는 requestId, errorCode, status와 함께 해석하며, 정확한 outbound phase 구분에는 추후 domain-boundary instrumentation이 필요하다.

archive POST는 report token 검증과 storage write가 하나의 domain 호출 안에 있으므로, storage 성공 전 실패는 provider가 비어 있을 수 있다. provider 부재를 Firestore가 호출되지 않았다는 확정 증거로 해석하지 않고 requestId와 errorCode로 조사하며, 실패 phase를 정확히 구분하려면 archive domain 내부 instrumentation이 추가로 필요하다.

다음 값은 로그, 경보 설명, 대시보드 라벨, 티켓, 채팅에 남기지 않는다.

- 이름, 생년월일, 출생 시각, 성별 등 입력 프로필
- 질문 본문, 리포트 본문, 요청·응답 body
- 이메일, 전화번호, Kakao 식별자 등 개인정보
- Authorization 헤더, 쿠키, 사용자·리포트·관리자 token
- API key, secret, 관리자 비밀번호 또는 해시 원문
- 원본 주문 ID, 결제 영수증 전체, 공급자 응답 원문
- 예외 객체 전체, 환경변수 덤프, HTTP 헤더 전체

orderHash는 재식별 가능성이 남은 가명 식별자다. 로그 접근 권한과 보존 기간을 제한하고, 고객에게 노출하거나 인증·인가 판단에 사용하지 않는다. 동일 해시가 충돌할 수 있으므로 조사 시 requestId, 시간, productId를 함께 사용한다.

PII 또는 비밀이 로그에 들어간 것이 확인되면 일반 장애가 아니라 보안 사고로 전환한다. 로그 접근을 즉시 제한하고, 노출된 비밀은 회전하며, 원문을 복사하지 않은 채 보안 담당자에게 에스컬레이션한다.

## 3. 요청 추적 절차

1. 고객에게 화면 또는 응답 헤더에 표시된 requestId와 대략적인 발생 시각만 요청한다.
2. requestId로 event=http_request 레코드를 찾는다.
3. route, status, latency, errorCode, productId, orderHash, provider, degraded를 확인한다.
4. 같은 orderHash를 볼 때는 짧은 시간 범위와 productId를 함께 제한한다.
5. 공급자 콘솔을 확인해야 하면 서버가 보관한 내부 결제 키로 권한 있는 운영자가 별도 조회한다. 로그에 원본 키를 추가하지 않는다.
6. 요청 body, 질문, 이름, 이메일을 재현용으로 수집하지 않는다. 필요한 경우 합성 개발 fixture로만 재현한다.

requestId가 없거나 유효하지 않으면 서버가 새 값을 발급한다. 프론트가 보낸 X-Request-ID와 응답 X-Request-ID를 연결하되, 이 값만으로 사용자나 주문을 신뢰하지 않는다.

## 4. Health 계약

health는 트래픽 라우팅 의도를 구분하며 외부 의존성 이름, 모델, 프로젝트, 컬렉션, 키 설정 여부를 노출하지 않는다.

| 의도 | 응답 요약 | 사용처 |
| --- | --- | --- |
| summary | ok, service, status, timestamp | 제한된 운영 요약 |
| liveness | ok=true, service, status=live, timestamp | 프로세스 재시작 판단 |
| readiness | ok, service, status=ready 또는 not_ready, timestamp | 신규 트래픽 수신 판단 |

liveness는 PortOne, Gemini, Firestore 등 외부 의존성 장애 때문에 실패시키지 않는다. readiness는 안전한 핵심 요청을 처리할 수 없는 구성 또는 내부 준비 실패 때만 not_ready로 한다. 상세 원인은 인증된 운영 로그에서 확인한다.

health 응답에 provider, model, secret 이름, 데이터베이스 상태 원문, 외부 오류 메시지를 추가하지 않는다. health 자체는 고비용 도메인 rate limit과 분리하고, 공개 엔드포인트 스캔에 대비한 낮은 비용의 독립 제한만 고려한다.

## 5. Rate limit과 실패 폐쇄

초기 기본값은 다음과 같다. 모든 버킷은 60초 창이며 운영 데이터로 조정한다.

| 범위 | 기본 한도 | 대표 작업 | 실패 정책 |
| --- | ---: | --- | --- |
| auth | 20 | Kakao 교환, 사용자 인증 | 제한 상태가 불명확하면 거부 |
| payment | 30 | 주문 생성, 결제 확인, entitlement 갱신 | 제한 또는 공급자 검증 실패 시 권한 미발급 |
| report | 12 | 유료 리포트 생성 | 제한 실패 시 생성 거부, 비용 폭주 방지 |
| admin | 5 | 관리자 로그인·조회 | 항상 실패 폐쇄 |

제한 키에는 범위와 서버가 신뢰한 네트워크·인증 식별자만 사용한다. token, 이메일, 원본 주문 ID를 키나 로그에 넣지 않는다. 프록시 헤더는 Cloud Run의 신뢰 경계에서 정규화된 값만 사용한다.

버킷 저장소가 용량 한도에 도달하거나 상태를 결정할 수 없으면 보호 대상 요청을 통과시키지 않는다. 응답은 errorCode=RATE_LIMIT_EXCEEDED와 retryAfterSeconds를 포함하고 Retry-After를 제공한다. scope는 응답 필드가 아니라 적용된 정책과 정규화된 route로 식별한다. 제한 초과는 결제 성공, report 권한, 관리자 권한으로 해석하지 않는다.

현재 프로세스 메모리 limiter는 Cloud Run 인스턴스별 한도이며 전역 한도가 아니다. 인스턴스를 둘 이상 운영하면 외부 공유 limiter로 교체해야 한다. 교체 전에는 최대 인스턴스·동시성·상위 게이트웨이 제한을 보완 통제로 두고, 이를 전역 rate limit이라고 보고하지 않는다.

429 비율이 높을 때 제한을 즉시 해제하지 않는다. 정상 트래픽인지 공격인지 먼저 확인하고, 필요하면 특정 범위의 용량만 단계적으로 조정한다. 관리자와 결제 확인의 실패 폐쇄는 장애 완화를 이유로 우회하지 않는다.

## 6. 공통 경보 기준

비율 경보는 최소 요청 수를 함께 둬 저트래픽 오탐을 줄인다. 분모에서 health와 명백한 클라이언트 취소를 제외한다.

| 신호 | 경고 | 긴급 |
| --- | --- | --- |
| 리포트 생성 지연 | report 완료 요청 20건 이상에서 p95 latency 25초 초과가 10분 | p95 45초 초과가 10분 또는 5xx·시간초과 5% 초과가 5분 |
| 결제 확인 실패 | 공급자·서버 errorCode 비율 2% 초과가 10분, 확인 10건 이상 | 5% 초과가 5분 또는 서버 오류 10건 연속 |
| AI fallback 증가 | report 20건 이상에서 degraded=true 또는 provider=deterministic-fallback 비율 10% 초과가 15분 | 30% 초과가 10분 또는 50% 초과가 5분 |
| archive 실패 | archive 요청 20건 이상에서 5xx 비율 1% 초과가 15분 | 5% 초과가 5분 또는 쓰기 실패 5건 연속 |
| rate limit 이상 | 범위별 429가 최근 기준선의 3배이며 10분 지속 | payment 또는 admin 범위에서 10배 급증, 공격 징후 동반 |
| 로그 안전 위반 | 금지 필드가 1건이라도 탐지 | 즉시 보안 사고 |

결제의 사용자 취소, 잘못된 입력, 소유권 불일치 같은 기대된 4xx는 공급자 장애율에서 제외하되 별도 보안·UX 지표로 본다. 401, 403, 409 급증은 자격 증명 공격, 재사용, 프론트 계약 불일치 가능성이 있어 errorCode별로 분리한다.

## 7. 공통 사고 대응

### 7.1 최초 10분

1. 사고 시작 시각, 영향 route, status, errorCode, productId, provider, degraded 비율을 기록한다.
2. 배포 직후라면 직전 정상 버전과 변경 범위를 비교한다.
3. health의 liveness와 readiness를 각각 확인한다.
4. 실제 고객 영향, 결제 금액, 주문 권한을 클라이언트 표시만으로 판단하지 않는다.
5. 원본 body나 공급자 오류 원문을 채팅에 붙이지 않는다.
6. SEV 수준을 정하고 담당자 한 명을 incident lead로 지정한다.

### 7.2 공통 완화 우선순위

1. 중복 결제와 무권한 리포트 노출을 막는다.
2. 안전한 읽기와 이미 완료된 결과 재사용을 유지한다.
3. 고비용 생성과 관리자 변경 작업은 실패 폐쇄한다.
4. AI 품질 저하는 degraded로 명시된 결정적 폴백이 허용되는 계약 안에서만 완화한다.
5. 데이터 삭제, 수동 entitlement 발급, 가격 변경은 즉흥적으로 수행하지 않는다.

### 7.3 복구 판정

- 경고 임계값 아래에서 최소 30분 유지
- readiness가 안정적으로 ready이고 liveness 재시작 반복 없음
- 신규 결제 표본이 공급자와 서버 원장 양쪽에서 일치
- 중복 entitlement 또는 중복 결제 없음
- 리포트 권한과 archive 소유권 검증 정상
- 완화 설정을 원래 값으로 되돌린 뒤 재발 없음

## 8. 리포트 생성 지연

### 조사

- route=report 계열의 latency p50, p95, p99와 status를 비교한다.
- provider별 지연과 degraded 비율을 분리한다.
- REPORT_GENERATION_IN_PROGRESS, 공급자 시간초과, 저장소 잠금 관련 errorCode를 구분한다.
- 같은 orderHash의 동시 요청 수와 기존 완료 결과 재사용 여부를 확인한다.
- 최근 배포, 모델 설정, 외부 제공자 상태, Cloud Run 인스턴스 포화도를 확인한다.

### 완화

- 동일 결제의 동시 생성은 하나만 허용하고 나머지는 Retry-After로 안내한다.
- 완료 캐시가 무결성 검사를 통과하면 재사용한다.
- AI 제공자 장애 시 계약된 결정적 폴백만 degraded=true로 제공한다.
- 임의로 생성 잠금을 삭제하거나 report token 검증을 우회하지 않는다.
- 필요하면 report 범위만 더 보수적으로 제한해 비용과 큐 증가를 막는다.

### 복구와 에스컬레이션

p95가 25초 아래에서 30분 유지되고 생성 잠금과 실패 상태가 정상적으로 정리됐는지 확인한다. 10분 이상 긴급 임계값이 지속되면 SRE와 report 도메인 담당자에게 에스컬레이션한다. 결제는 성공했으나 결과를 영구 제공하지 못하면 고객지원 책임자도 참여시킨다.

## 9. 결제 확인 실패

### 조사

- payment confirm route에서 공급자·서버 5xx와 기대된 4xx를 분리한다.
- productId, orderHash, errorCode, status, provider를 확인한다.
- 서버 카탈로그 가격, 주문 claim, 사용자 소유권, 공급자 결제 상태가 모두 일치했는지 권한 있는 내부 도구로 확인한다.
- 공급자 상태 페이지, API 지연, 인증 실패 여부를 확인하되 secret 값을 출력하지 않는다.
- 동일 orderHash 재시도가 원자적으로 하나의 entitlement만 만들었는지 확인한다.

### 완화

- 공급자 확인이 불가능하면 결제 성공으로 처리하지 않고 권한을 발급하지 않는다.
- 브라우저가 보낸 금액, 상품, 성공 플래그만으로 수동 승인하지 않는다.
- 이미 확인된 동일 결제의 안전한 멱등 재시도만 허용한다.
- 결제 상태가 불명확하면 고객에게 재결제를 유도하지 말고 확인 대기 상태로 안내한다.
- 관리자 화면에서 임시 가격 변경이나 원장 직접 쓰기를 하지 않는다.

### 복구와 에스컬레이션

신규 표본 결제의 공급자 금액·상품·상태와 서버 원장이 일치하고 오류율이 30분 정상이어야 복구다. 중복 과금, 잘못된 금액, 타 사용자 권한 발급 가능성이 한 건이라도 있으면 즉시 SEV-1로 올리고 payment 담당자와 보안 담당자를 호출한다.

## 10. AI fallback 증가

### 조사

- report 요청 중 degraded=true와 provider=deterministic-fallback 비율을 계산한다.
- 공급자 시간초과, 할당량, 응답 형식 검증, 콘텐츠 검증 errorCode를 분리한다.
- productId별 편향과 최근 프롬프트·모델 설정 변경을 확인한다.
- 환경변수는 값이 아니라 설정 여부와 버전만 확인한다.
- 폴백 결과가 샘플 또는 실데이터로 오인되지 않고 계약된 결정적 결과인지 확인한다.

### 완화

- 유료 결과 계약이 허용하는 경우에만 결정적 폴백을 degraded=true로 반환한다.
- 공급자 장애 중 무제한 재시도를 금지하고 지수 백오프와 report 제한을 유지한다.
- 검증 실패 결과나 공급자 원문을 사용자에게 그대로 노출하지 않는다.
- 모델 키를 코드나 임시 환경 파일에 복사하지 않는다.
- 품질 계약을 만족하지 못하면 성공으로 가장하지 말고 재시도 가능한 표준 오류를 사용한다.

### 복구와 에스컬레이션

fallback 비율이 10% 아래에서 30분 유지되고 정상 provider 표본의 형식·콘텐츠 검증이 통과해야 한다. 30% 초과가 10분 지속되면 SRE와 AI/report 담당자에게 에스컬레이션한다. 안전 필터 우회 또는 민감 내용 노출 가능성이 있으면 보안 담당자를 즉시 포함한다.

## 11. Archive 실패

### 조사

- archive 읽기와 쓰기를 분리하고 401·403과 5xx를 구분한다.
- requestId, route, errorCode, orderHash, productId만 사용해 추적한다.
- Firestore 등 저장소의 권한, 할당량, 지연, 조건부 쓰기 충돌을 확인한다.
- 쓰기 응답이 실패했는데 UI가 성공으로 표시했는지 확인한다.
- archive 소유권과 report token의 결제·상품 결합이 유지되는지 확인한다.

### 완화

- 저장 실패를 성공으로 응답하거나 로컬 저장만으로 보관 완료라고 표시하지 않는다.
- 안전한 읽기가 가능하면 읽기는 유지하고 쓰기만 명시적으로 실패시킨다.
- 재시도는 동일 사용자·주문·상품의 멱등 계약 안에서 수행한다.
- 원본 리포트나 개인정보를 로그, 티켓, 임시 파일로 복사하지 않는다.
- 권한 검증 또는 저장 상태가 불명확하면 archive 쓰기를 실패 폐쇄한다.

### 복구와 에스컬레이션

새 archive 쓰기와 읽기 표본이 소유권 검증을 포함해 성공하고 5xx 비율이 30분 정상이어야 한다. 데이터 유실, 타 사용자 열람, 소유권 우회 가능성이 있으면 즉시 SEV-1로 올리고 archive 담당자와 보안 담당자를 호출한다.

## 12. 환경변수와 배포 점검

서버 시작 시 환경변수 형식, 범위, 필수 조합을 검증한다. 운영 필수 값이 없거나 약한 비밀, 잘못된 숫자, 허용되지 않은 origin, 서로 같은 signing secret은 시작을 중단해야 한다.

점검 시 환경변수 전체를 출력하지 않는다. 이름별 configured=true/false, 비밀 관리자 버전 활성 여부, 마지막 회전 시각만 확인한다. 실제 키를 로컬 메모, CI 로그, PR 설명에 넣지 않는다.

배포 전후 확인 항목은 다음과 같다.

- npm run lint
- npm run test
- npm run build
- npm --prefix cloudrun-api run build
- 보안 헤더 계약 검사
- PR 의존성 변경 검토와 고위험 npm audit
- 전체 Git 이력 secret scan
- summary, liveness, readiness health 응답의 최소 정보 계약
- auth, payment, report, admin rate-limit과 Retry-After
- 로그 샘플에 금지 필드가 없는지 확인

보안 검사를 예외 처리해야 하면 만료 시각, 소유자, 근거, 보완 통제를 기록한 승인 절차가 필요하다. 탐지 규칙을 통째로 끄거나 실제 비밀을 allowlist에 넣지 않는다.

## 13. 에스컬레이션 기준

| 등급 | 예시 | 호출 |
| --- | --- | --- |
| SEV-1 | 중복 과금, 타 사용자 리포트 노출, 관리자 우회, PII·secret 로그 | incident lead, SRE, 도메인 담당, 보안·개인정보 담당 즉시 |
| SEV-2 | 결제 확인 또는 archive 긴급 임계값, report 대규모 불가 | SRE와 해당 도메인 담당 10분 내 |
| SEV-3 | 경고 임계값, 제한된 degraded 증가 | 업무 시간 내 담당자, 추세 감시 |

외부 공급자 티켓에는 requestId, 시간 범위, 비식별 errorCode, provider 측 자체 요청 식별자만 제공한다. 이름, 생년월일, 질문, 이메일, token, secret, 원본 주문 ID는 보내지 않는다.

사고 종료 후 2영업일 안에 탐지 시각, 영향 범위, 원인, 완화, 복구 검증, 재발 방지 조치를 기록한다. 보고서에도 실제 개인정보와 비밀은 포함하지 않는다.
